# Tenants

> Manage tenants, deployments, environments, and backups from the CLI

Tenants are database-isolated environments within a workspace, each with their own data and configuration. The CLI provides full lifecycle management for tenants and their backups.

> [!NOTE]
>
> Tenant commands require a workspace ID, either from your profile or via the `-w` flag. Most tenant commands identify tenants by their **name** (e.g., `t1234-abcd-xyz1`), not a numeric ID.

> [!TIP]
>
> Need a short-lived tenant that cleans itself up — for a preview, a CI run, or a throwaway experiment? See [ephemeral tenants](https://docs.xano.com/xano-cli/ephemeral.md), which auto-expire and, unlike regular tenants, accept a direct `push`.

## CRUD

### List Tenants

Terminal

```bash theme={null}
xano tenant list
```

Each tenant shows its name, state, license, and — when available — the **cluster**, **platform**, and **release** it is running on. Use `-o json` for the full JSON response.

### Get Tenant Details

Terminal

```bash theme={null}
xano tenant get TENANT_NAME
```

The output includes the tenant's name, state, license, domain, cluster, release, platform, version, and deployment details.

### Create a Tenant

Terminal

```bash theme={null}
xano tenant create "My Tenant"
```

| Argument / Flag | Description |
| - | - |
| `display` | Display name (required, positional) |
| `-d` | Description |
| `--type` | Tenant type: `tier1` (default), `tier2`, `tier3` |
| `--cluster_id` | Cluster ID (required for tier2/tier3) |
| `-l, --license` | Path to a license override file to apply during creation |
| `--platform_id` | Platform ID to use |
| `--domain` | Custom domain |
| `--[no-]ingress` | Enable/disable ingress (default: enabled) |
| `--[no-]tasks` | Enable/disable background tasks (default: enabled) |
| `--required_reviewers` | Minimum number of distinct approvals required before a Deployment Request can deploy (0–10, default: 0 / gate off). See [Deployment Requests](https://docs.xano.com/xano-cli/tenant-deploy-requests.md) |
| `--[no-]allow_deploy_bypass` | Allow users with the deploy bypass permission to skip the review gate (default: disabled) |
| `--[no-]allow_quick_deploy` | Automatically deploy a request as soon as it reaches the required approvals (default: disabled) |
| `-w` | Workspace ID |
| `-o` | Output format: `summary` or `json` |

### Edit a Tenant

Terminal

```bash theme={null}
xano tenant edit TENANT_NAME --display "New Name" -d "Updated description"
```

Additional flags: `--domain`, `--proxy`, `--[no-]ingress`, `--[no-]tasks`, `--[no-]rbac`, `--required_reviewers`, `--[no-]allow_deploy_bypass`, `--[no-]allow_quick_deploy`.

### Delete a Tenant

Terminal

```bash theme={null}
xano tenant delete TENANT_NAME
```

Add `-f` to skip the confirmation prompt.

> [!WARNING]
>
> Deleting a tenant destroys all associated infrastructure and data. This cannot be undone.

## Impersonate

Open a tenant's dashboard in your browser, or retrieve the impersonation URL for scripting.

Terminal

```bash theme={null}
xano tenant impersonate TENANT_NAME
```

Print the URL without opening the browser:

Terminal

```bash theme={null}
xano tenant impersonate TENANT_NAME --url-only
```

Output credentials as JSON:

Terminal

```bash theme={null}
xano tenant impersonate TENANT_NAME -o json
```

## Pull & Push

You can pull a tenant's content down as local XanoScript files, or push local files to a tenant. This works the same way as [workspace pull & push](https://docs.xano.com/xano-cli/push-pull.md), but targets a specific tenant.

### Pull a Tenant

Terminal

```bash theme={null}
xano tenant pull -d ./my-tenant -t TENANT_NAME
```

| Flag | Description |
| - | - |
| `-t` | Tenant name (required) |
| `--env` | Include environment variables |
| `--records` | Include database records |
| `--draft` | Include draft versions of resources |
| `-w` | Workspace ID |

> [!NOTE]
>
> Direct tenant push is not supported. To deploy changes to a tenant, create a release and deploy it with `xano tenant deploy_release`, or use the [sandbox workflow](https://docs.xano.com/xano-cli/sandbox.md) (`xano sandbox push`).

## Deployments

### Deploy a Release

Deploy a release to a tenant by name:

Terminal

```bash theme={null}
xano tenant deploy_release TENANT_NAME --release v1.0
```

| Flag | Description |
| - | - |
| `-r, --release` | Release name to deploy (required) |
| `--[no-]transaction` | Wrap deployment in a database transaction (default: enabled) |
| `-w` | Workspace ID |
| `-o` | Output format: `summary` or `json` |

> [!NOTE]
>
> If the tenant has **Require Deployment Request** enabled (`required_reviewers > 0`), this command checks first whether an approved request already exists for that tenant and release. If one doesn't, the deploy is rejected with guidance to create one via `xano tenant_deploy_request create` instead. See [Deployment Requests](https://docs.xano.com/xano-cli/tenant-deploy-requests.md).

### Deploy a Platform

Terminal

```bash theme={null}
xano tenant deploy_platform TENANT_NAME --platform_id 5
```

| Flag | Description |
| - | - |
| `--platform_id` | Platform ID to deploy (required) |
| `--license` | Path to a license override file to apply after deployment |
| `-w` | Workspace ID |
| `-o` | Output format: `summary` or `json` |

## Tenant License

Terminal

```bash theme={null}
# Get tenant license (saves to file by default)
xano tenant license get TENANT_NAME
xano tenant license get TENANT_NAME --view

# Set tenant license from file
xano tenant license set TENANT_NAME --file ./license.yaml
xano tenant license set TENANT_NAME --value "inline-license-content"
```

## Tenant Environment Variables

Manage environment variables on a per-tenant basis.

### List Env Var Keys

Terminal

```bash theme={null}
xano tenant env list TENANT_NAME
```

### Get a Single Env Var

Terminal

```bash theme={null}
xano tenant env get TENANT_NAME --name DATABASE_URL
```

### Set an Env Var

Terminal

```bash theme={null}
xano tenant env set TENANT_NAME --name DATABASE_URL --value "postgres://..."
```

### Delete an Env Var

Terminal

```bash theme={null}
xano tenant env delete TENANT_NAME --name DATABASE_URL
```

### Export All Env Vars

Export all environment variables to a YAML file:

Terminal

```bash theme={null}
xano tenant env get_all TENANT_NAME
xano tenant env get_all TENANT_NAME --file ./env.yaml
```

### Import All Env Vars

Import environment variables from a YAML file (replaces existing):

Terminal

```bash theme={null}
xano tenant env set_all TENANT_NAME
xano tenant env set_all TENANT_NAME --file ./env.yaml --clean
```

## Tenant Backups

### List Backups

Terminal

```bash theme={null}
xano tenant backup list TENANT_NAME
```

Use `--page` for pagination.

### Create a Backup

Terminal

```bash theme={null}
xano tenant backup create TENANT_NAME
```

### Restore from a Backup

Terminal

```bash theme={null}
xano tenant backup restore TENANT_NAME --backup_id 10
```

You'll be asked to confirm before the restore proceeds. Use `-f` to skip confirmation.

> [!WARNING]
>
> Restoring a backup replaces the current tenant data entirely.

### Export a Backup

Download a backup as a `.tar.gz` file:

Terminal

```bash theme={null}
xano tenant backup export TENANT_NAME --backup_id 10
```

Specify a custom output path with `--output`:

Terminal

```bash theme={null}
xano tenant backup export TENANT_NAME --backup_id 10 --output ./backups/my-backup.tar.gz
```

### Import a Backup

Import a backup file into a tenant:

Terminal

```bash theme={null}
xano tenant backup import TENANT_NAME --file ./my-backup.tar.gz
```

### Delete a Backup

Terminal

```bash theme={null}
xano tenant backup delete TENANT_NAME --backup_id 10
```

Add `-f` to skip the confirmation prompt.

## Ephemeral Tenants

An [ephemeral tenant](https://docs.xano.com/xano-cli/ephemeral.md) is a regular tenant with a timer on it. It belongs to a workspace and gets its own database, environment variables, and configuration — but it deletes itself when its window elapses, so there is no cleanup step to forget.

Two differences matter when you're choosing between them:

| | Tenant | Ephemeral tenant |
| - | - | - |
| Lifetime | Until you delete it | Auto-expires (`--expires-hours`, 1–24) |
| Getting code in | Deploy a [release](https://docs.xano.com/xano-cli/releases.md) from a source workspace | Accepts a direct `xano ephemeral push` from local files |

That second row is the reason to reach for one: a regular tenant receives logic through the release pipeline, while an ephemeral tenant takes a push straight from your working directory — so you can stand up a running environment from a branch that has never been released.

### With the CLI

Every `xano tenant` verb has an `xano ephemeral` counterpart. A full cycle:

Terminal

```bash theme={null}
xano ephemeral create "PR #482 preview" --expires-hours 4 -w 5
xano ephemeral push TENANT_NAME -d ./my-workspace --dry-run
xano ephemeral push TENANT_NAME -d ./my-workspace --records --env
xano ephemeral impersonate TENANT_NAME --guest --url-only
xano ephemeral delete TENANT_NAME
```

See [Ephemeral Tenants](https://docs.xano.com/xano-cli/ephemeral.md) for the full command reference.

### In CI/CD

Create one per pipeline run, push the commit under test with real records and environment variables, run your checks against it, then delete it early rather than waiting on the timer. `-f` skips the confirmation prompt, and `-o json` returns the tenant name for your script to capture.

Terminal

```bash theme={null}
xano ephemeral create "CI run" --expires-hours 2 -w 5 -o json
xano ephemeral push TENANT_NAME -d ./my-workspace --records --env --force --wait
xano ephemeral delete TENANT_NAME -f
```

Because each run gets a clean environment, tests never inherit state from the last one, and parallel runs can't collide. For the surrounding release process, see [CI/CD](https://docs.xano.com/ci-cd); for driving this loop with an AI coding agent, see [Agentic Development](https://docs.xano.com/getting-started-ai.md).
